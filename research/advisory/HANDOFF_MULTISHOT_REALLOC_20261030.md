# 交接：多次容量重分配（multi-shot realloc）——高方差，需重写判据

2026-10-30 22:40 +08:00，DeepSeek 侧交接给 Codex。**本条不是结论推荐，是求助**：
多重分配质量提升明显但结果不可复现，需要基础设施层面的修复才能判断去留。

## 1. 机制

交付配方中的一次「重分配」：在训练某一步，退役 15% 最低贡献（`opacity × mean_scale`）的高斯，
把释放的名额分给梯度最高的 7.5% 高斯各分裂成两个（位置加 `randn × scale × 0.3` 抖动、尺度 ÷1.6）。
多次重分配 = 在结构阶段内重复该操作 N 次。

实现位置：`research/train_sweep.py` 训练循环内 `--realloc_frac` / `--realloc_at` 分支。
`--realloc_at` 支持逗号分隔的多个步数（如 `250,500,750,1000,1250,1500,1750,2000`）。
`--realloc_mode {concat,inplace}`、`--realloc_select {argsort,topk}` 两个开关是本轮新增。

## 2. 已测数据（务必注意方差）

场景 `mipnerf360/bicycle`，同一 init PLY（ReSplat world），同一配方其余参数，
单卡顺序执行（除非注明）：

| 运行 | 配置 | 质量分 | B 秒 | 备注 |
|---|---|---:|---:|---|
| rr5 | 8-shot concat+argsort | **10.86** | 42.1 | 3 卡并发 |
| rr6 | 12-shot concat+argsort | 12.19 | 85.3 | 3 卡并发 |
| sq | 1-shot（inplace 默认） | 10.04 | 29.8 | 顺序 |
| sq | 8-shot（inplace 默认） | **6.52** | 28.3 | 顺序 |
| rs | 8-shot concat+**topk** | **6.55** | 28.4 | 顺序，显式 mode |
| sel | 8-shot concat+**argsort** | **10.93** | 44.1 | 顺序，显式 select |
| sel | 8-shot concat+**topk** | **10.86** | 44.1 | 顺序，显式 select |

其它场景（3 卡并发，rr5/rr6）：
- dl3dv/0f622ea：1-shot q 17.91 → 8-shot 23.03 → 12-shot 26.56
- dl3dv/3e4dbe：1-shot q 21.44 → 8-shot 24.76 → 12-shot 28.42

**核心矛盾**：`rs(concat+topk)` = 6.55 与 `sel(concat+topk)` = 10.86 是**完全相同的配置**，
同 GPU、同顺序执行、同 init。质量差 4.3 分、B 差 15.7 秒。

## 3. 两个怀疑点（按可能性排序）

### 3.1 早期重分配使用了未累积的统计（最可能）
第一次重分配发生在第 250 步。此时 FastGS 的 `xyz_gradient_accum_abs / denom` 基本为空
（denom≈0），`argsort/topk` 在大量并列零值上取出的集合近乎任意 → 分裂源近似随机。
8 次串联把这次分叉放大。**建议**：把第一次重分配推迟到梯度统计稳定之后（例如 ≥1000 步），
或对 `grad` 加空值保护（denom 过小时跳过该次重分配）。

### 3.2 RNG 流未隔离
重分配的 `randn` 抖动与训练相机采样（`random.randint`）共用全局 RNG，
多次调用会改变后续相机序列 —— 同 seed 不等于同轨迹。**建议**：
重分配使用独立的 `torch.Generator`，并在记录里保存每次重分配的实际源索引摘要（hash）。
（决策板 §seed 稳健性 已提出同类要求。）

### 3.3 已排除
- **不是 argsort vs topk 的差异**：同配置两者 10.93 vs 10.86。
- **不是优化器重建开销**：`inplace`（O(n) 原地写）与 `concat`（3 次全量拷贝）的 B 秒数几乎相同
  （28.3 vs 28.4），所以「每次 4~5 秒」的旧推断错误。
- **不是并发导致的（对质量而言）**：sq/rs/sel 全是顺序执行，仍出现 6.52/6.55/10.86。
  但**并发确实抬高了 B 秒数**（同配置 28~44 秒），所有涉及 TIME 的历史结论都需要单卡串行重测。

## 4. 建议的验证协议（若继续）

1. 固定重分配判据：跳过 denom 不足的前期，只用稳定后的梯度统计；
2. 每配置跑 **≥3 次**（不同 seed），报告**中位数与范围**，不用单次数值做采纳/否决；
3. 记录每次重分配的源/目标索引摘要、实际更新的参数 hash；
4. 先只验证 1-shot vs 2-shot vs 3-shot（低次数），确认低次数是否稳定；
   历史上的 +5 分提升都出现在 8 次以上，低次数未知。
