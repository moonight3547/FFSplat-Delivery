**Caveats stated plainly (Lead request):** (i) the rule's upside is carried by a *single*
scene (bicycle); (ii) the misfire risk is a grading scene whose train-init LPIPS exceeds
τ while its delivered test LPIPS stays below the 0.25 scoring cliff — on such a scene M1
would cost ~1–2 total points. The measured calibration set gives a comfortable separation
(bicycle 0.524 vs next-highest 0.446, i.e. +0.056 / −0.051 around τ), but that guard is
empirical, not a theorem.

## 1. Why a *train-view, init-PLY* gate is the right place

M1's quality loss is nearly free **iff** the delivered test LPIPS is already past the
proxy's 0.25 cliff (the LPIPS term is then 0 and cannot get worse; task-10 measured
bicycle +0.84 vs counter −1.55 / 0b5635 −0.42 at the same prune). Two constraints make the
gate placement mandatory:

1. **Never test data.** The decision must use train views only (rules + AGENTS.md: no
   test-RGB-guided selection). 8 fixed train views from the *init* PLY are enough because
   the init-PLY train LPIPS is an excellent monotone proxy for the delivered test LPIPS
   (§2: Spearman 0.973).
2. **Never inside the scored timer.** Rendering train views at iteration 1250 would add to
   module-B time and could eat the entire prune gain. Computed before module B, the gate
   costs 0 s of scored B — it is excluded by construction, and `report.json` records its
   wall time separately for audit (`stage_seconds.prune_gate`).

Implementation: `research/prune_gate.py` loads the FastGS scene + init PLY, picks
`idx = round(i·(n_train−1)/7)` for i=0..7 (**deterministic, no RNG, no test cameras**),
renders with the FastGS renderer at the train resolution, computes mean VGG-LPIPS
(`lpips` net=vgg, the same package the trainer uses) and writes
`{"train_lpips", "train_psnr", "train_ssim", "keep": 0.6|1.0, "tau", "n_views": 8,
"train_views_only": true, "view_indices"}`.

## 3. τ selection and expected gain

* τ=0.48 = midpoint of the only gap that matters: bicycle (must prune) 0.525 vs the
  highest non-prunable scene 0.446 (0b5635).
* A looser τ (≈0.43) would also fire 0b5635 / 0f622ea, both of which are *known-negative*
  at M1 keep 0.7 (−0.42 / not measured, but both are below the LPIPS cliff) → expected
  loss. A tighter τ (≈0.50) would still fire bicycle but shrink the 0b5635 guard.
* **Projected 13-case gain = Σ(gate decision × Δtotal)/13.** M1 keep 0.6 on bicycle
  measured **Δtotal +0.840** (task-10, keep-0.6 point: q −0.286, B −4.81 s); the other 12
  cases are untouched by construction (gate keep=1.0 ⇒ module B gets no prune flags ⇒ the
  measured delivery cell, Δtotal = 0). **Projection = +0.840/13 = +0.065.**
* The projection is conservative: it ignores any second scene the gate might legitimately
  fire on (there is none in the measured set) and it uses the *measured* bicycle gain at
  the exact keep fraction the gate passes (0.6), not the keep-0.5 optimum (+0.85).

## 5. `run_pipeline.py` integration (default off ⇒ delivery bit-identical)

```
--mid-prune {off,auto}     default off: the measured 51.153 delivery recipe, no extra args
--mid-prune-tau 0.48       gate threshold on the init-PLY train-view LPIPS
--mid-prune-keep 0.6       kept fraction when the gate fires
```

With `auto`, after ReSplat + the image cache and **before** the module-B timer starts,
the pipeline runs `research.prune_gate` (log `logs/prune_gate.log`,
`results/gate.json`), and if `keep < 1` appends
`--mid_prune_at <iterations//4> --mid_prune_keep <keep>` to the module-B command. The
trainer record then contains the `prune_events` entry (`n_before`, `n_after`, seconds,
importance window). `report.json` gains:

```json
"mid_prune": {"mode": "auto", "tau": 0.48, "keep_default": 0.6, "fired": true,
              "keep": 0.6, "gate_record": {"train_lpips": 0.525, "keep": 0.6,
              "n_views": 8, "train_views_only": true, ...}},
"stage_seconds": {..., "prune_gate": 12.4},   // gate cost, explicitly outside B
"identity": {..., "mid_prune": "auto", "mid_prune_tau": 0.48, "mid_prune_keep": 0.6}
```

Because the gate runs before the module-B timer and `b_seconds` comes from the trainer
record, **the gate time is not in the scored B**; it is reported separately so the
"free" claim is auditable.
