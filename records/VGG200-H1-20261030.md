# VGG100 vs VGG200 inside 5000 steps, on the 5K-D3500 base — H1, 5 bad cases

**Task-17 (user 2026-10-31 "H1测试一下VGG200的结果"; re-scoped twice: BigD2500
first, then user-directed 5K-D3500). Verdict: ADOPT the in-run VGG tail. VGG200
is positive on all 5 cases, mean Δtotal = +2.99 (min +1.12, max +4.64), driven by
the LPIPS term exactly as the 0.25-cliff model predicts. VGG100 is also positive
everywhere (mean +2.56) and is the cheaper variant.**

All data measured on H1 (`ffh1`), strictly serial, quiet-box gated, commit
**`5f616b3`**, recipe **5K-D3500**, official metrics. Raw evidence:
`records/vgg200-h1-20261030/` (15 rows + per-cell `summary.json` /
`train_record.json` / `metrics.json`), H1
`outputs/vggab-d3500-20261030/`. No git push.

## 1. Question and the cliff hypothesis

The earlier VGG direction was closed on **mipnerf360/bicycle** with the old
1250-window recipe, where the delivered LPIPS was 0.3030 — **above the 0.25
scoring cliff**, so the 40-point LPIPS term was already 0 and the extra phase only
cost PSNR/SSIM. The DL3DV bad cases sit near the cliff
(`LPIPS points = 40·clamp((0.25−LPIPS)/0.20)`), where 0.01 LPIPS = 2 quality
points. The hypothesis: a short full-resolution VGG tail **inside the same 5000
steps** converts LPIPS gains directly into score where LPIPS is near/above the
cliff. This run tests it on 5 cases (the 3 DL3DV bad cases + counter + bicycle,
the last as the historical above-cliff case), under the user-directed D3500 base.

  * `vgg100` — `--lpips-weight 0.1 --lpips-scale 1.0 --lpips-start 4901
    --lpips-end 5000` (active 4901–5000);

  `mipnerf360-counter`, `mipnerf360-bicycle`. One **shared in-session ctrl per

* Init PLYs = clean13 ReSplat outputs
  (`outputs/clean13-20261030/resplat/<tag>/resplat_world.ply`); work dirs = the

  `os.getloadavg()` on this pod returns the *physical host* load — 13–21 from

  `/proc/loadavg`, otherwise the gate never clears.)
* Per cell: PSNR/SSIM/LPIPS/`lpips_points`/q/B/TIME/total; `recipes_sha256`,

* **Historical D2500 row is preserved but excluded:** the user switched to D3500
  mid-run; the single completed D2500 ctrl row lives in
  `outputs/vggab-20261030/results.jsonl` (total 34.84) and is not used as a

## 6. Mechanism check (the cliff)

* The gain is **entirely the LPIPS term**: ΔLPIPS-points is `+2.0 … +6.8` on all
  ten pairs, while PSNR moves −0.28…+0.03 dB and SSIM −0.0055…−0.0020, costing
  only ~0.1–0.6 q.
* Ranking by LPIPS "reachability of the cliff" matches: **bicycle** (D3500 ctrl
  LPIPS 0.2559, just *above* the cliff → 0 LPIPS points) gains the most
  (+4.6 total: 0.2559→0.2158 crosses the cliff), **counter** (0.1735, deep below,
  little headroom left) gains the least (+1.1). That is the cliff model working
  in both directions.
* **Important correction to the old record:** the historical bicycle *negative*
  was measured on the old 1250-window recipe where its LPIPS was 0.3030. Under
  5K-D3500 its ctrl LPIPS is 0.2559, so the same VGG tail now pulls it under the
  cliff and it becomes the *largest* win. Bicycle is therefore **not a negative
  control under D3500** — it is a near-cliff case. The negative result was
  recipe-specific, not evidence that VGG "doesn't work".

primary; `vgg100` if B headroom matters** (it captures ~86 % of the mean gain for
~49 % of the B cost).

## 9. Caveats / open points

1. **5 cases only.** The three DL3DV bad cases + counter + bicycle were chosen by
   the Lead; the other 8 clean-13 cases (including hw) are untested with this
   arm. LPIPS on most other cases is far below the cliff, so the expected gain
   there is small-to-zero — the uniform-13-case Δtotal would be roughly the mean
   over cases that sit near the cliff.
2. **B timing:** the box was quiet-gated for every cell, but two cells report
   `loadavg_at_start` 3.98 / 4.36 (the gate threshold is <4); the arms within a
   case are interleaved ctrl→vgg100→vgg200 so any slow drift would mildly favour
   later arms on B — the paired quality gain is unaffected, and the ΔB values are
   self-consistent across cases. For a delivery-timing decision, re-measure the
   chosen arm on a fully quiet box.
3. The `stage3_seconds` field is 0 by design: the VGG term is **inside** the 5000
   steps, not a continuation (Codex semantics, confirmed by the Lead).
4. D2500 rows are historical only; they are not controls here.
5. Audit note if ever re-run with a **different** base: `train_record` only writes
   `actual_native_parameters` when the merged trainer path is used; a cell whose
   events list is empty must be treated as "did not use the merged trainer" and
   flagged rather than accepted (none here).
