## 7. 结论与建议

1. 基线复测可信：三例 49.63 分，与赛方基线一致。
2. 在不改前馈、16 视角、固定权重的约束下，**三例代理分现实区间是 50–62**；
   75 需要质量突破（尤其 hw），不是调参能到。
3. 若评价按赛方原文（经典 3DGS 30K 预算），可用更长 B，历史 MCMC 质量即可到 62.7，
   再把 B 压到 150 秒以内有望摸到 70。
4. 若要冲 75，最可能的两条路：hw 的位姿/几何修正（A 侧），
   以及在 ~90 秒内把高斯数推到 1M+ 的快速致密化 B。

## 15. MCMC（Taming-3DGS）作为模块 B：扫了容量/细化节奏/预算，仍输给 FastGS

在 4 台机器、12 张卡上跑了 MCMC（gsplat MCMCStrategy，独立 trainer `research/mcmc_budget.py`），

满血卡结果（质量分 = PSNR/SSIM/LPIPS 三项代理分；B = 模块 B 实测秒数）：

| 场景 | MCMC 最佳（配置） | B 秒 | FastGS 交付（5k 步） | B 秒 | 谁赢总分 |
|---|---|---|---|---|---|
| hw/billboard | q 36.38（90s、上限×3、细化50） | 77.2 | q 36.00（raw init） | 25.8 | **FastGS**（TIME 16.5 vs 5.1） |
| mip360/counter | q 35.90（90s、上限×3） | 77.9 | q 38.19 | 33.2 | **FastGS**（质量也更高） |
| DL3DV | q 62.98（90s、上限×3、细化50） | 77.7 | q 64.17 | 33.5 | **FastGS** |

MCMC 全网格（27 组实测）：hw 上限×2/×3/×4 → 36.01/36.33/35.88；细化 100→50 → 36.33→36.38（无差别）；
预算 45→90 秒 → 31.5→36.4（涨质量但 TIME 从 12.3 掉到 5.1）。counter 上限×3 比 ×2 高 6.4 分，
说明 MCMC 需要更多基元才收敛，但代价是每步更慢。**结论不变：同等质量下 MCMC 的时间成本约为 FastGS 的 3 倍。**

结论：
1. MCMC 的**质量上限和 FastGS 相当**（hw 36.4 vs 36.0，差 0.4 分），但达到同样质量需要
   ~3 倍的模块 B 时间；在 100 秒预算、TIME 占 20 分的口径下，总分反而低 8~11 分。
2. 提高上限（×3→×4）没有帮助（hw 36.33→35.88），细化间隔 100→50 无差别（±0.05），
   预算 45→90 秒才有明显提升但 TIME 损失更大。**不是没调够，是每质量点的时间成本更高。**
3. 因此模块 B 继续用 FastGS；MCMC 只在「预算宽松（>250 秒）」时才值得。

## 16. E0：解码缓存是纯系统收益（+0.9 均值，质量不变）

模块 B 的墙钟里包含用 PIL 解码 prepared PNG 的时间（DL3DV 288 张 ≈ 5.4 秒、counter ≈ 5.2 秒、
hw 56 张 ≈ 0.9 秒）。A 是我们自己的阶段，把同一批像素预解码成一个 uint8 数组是合法的管线改动，
不是把计时搬到别的阶段：每个阶段仍读同样的像素。

## 19. E8 诊断：模块 B 的时间结构（hw，5000 步，train 30.8 秒）

按 codex advisory 的 E8 建议先做计时拆解，再决定是否适配稀疏优化器：

| 区段 | 秒 | 占比 |
|---|---:|---:|
| 渲染（含结构统计） | 9.26 | 30.3% |
| loss 计算（L1+SSIM） | 1.75 | 5.7% |
| 反向传播 | 12.81 | 41.9% |
| **优化器 step** | **6.73** | **22.0%** |

优化器占 22% 是本次最有信息量的系统发现：FastGS 自带的 step 频率日程（每步 dense Adam +
每 16 步 SH）在我们的 5000 步预算内**从未进入降频区间**（它的降频从 15000 步才开始）。
按 Amdahl 上界，把优化器步频减半最多可省约 3.4 秒 ≈ +0.7 TIME 分。

对应实验（`opt_every.sh`，`--opt_step_schedule 2500:2` / `0:2`）正在跑：
前 2500 步完全不变，之后每 2 步一次并同步放大 LR 以保持单步位移。
若质量不掉且实际 B 秒下降，这就是一条纯系统收益；若质量掉，则说明 dense Adam 的每步更新
在短预算下不可省，记录为反例。

## 21. E8-lite（降低优化器步频）——证伪

诊断显示优化器占 train 的 22%（按同步计时），理论上步频减半可省约 3.4 秒。实测（同配方、同卡）：

| 配置 | counter B / 质量 / 总分 | hw B / 质量 / 总分 |
|---|---|---|
| 对照（每步 dense Adam） | 27.90s / 38.11 / **53.63** | 25.75s / 35.96 / **52.43** |
| 2500 步后每 2 步 | 28.48s / 37.98 / 53.36 | 25.44s / 35.91 / **52.45** |
| 全程每 2 步 | 24.97s / 37.16 / 53.39 | 25.40s / 35.75 / 52.29 |

**结论：无收益**（均值 53.03 → 52.91 / 52.84，最好情况只是持平）。

(2) 放大 LR 的做法改变了更新轨迹，质量略降。与 codex advisory 的止损条件一致——按 Amdahl
上界不足以覆盖 LR 补偿与轨迹改变的代价，停止该路线。

| 场景 | FastGS 交付 | 3DGS-MCMC | **孔洞注入** | 注入 vs FastGS |

| 场景 | 交付配方 B / q / 总分 | 孔洞注入 B / q / 总分 | 质量差 | 总分差 |

| dl3dv/0f622ea | 33.0s / 15.67 / **30.11** | 60.8s / 16.17 / 24.06 | +0.50 | **−6.05** |

   **选图不是当前流水线的瓶颈**，瓶颈是前馈重建本身对高频纹理/细结构的表达能力。
   本方向关闭，不再投入。

## 35. B｜固定预算的高斯重分配：三个场景全部胜出（质量+时间双改善）

实现（`--realloc-frac F --realloc-at 1250`，一次、总数不增长）：
在结构阶段末尾，按 `opacity × mean_scale` 退役贡献最低的 F 比例基元，
把腾出的名额 split 给「视空间梯度累积最高」的 F/2 个高残差基元（每个分 2 个、尺度 /1.6、位置加 0.3σ 抖动）。
总数基本不变，所以不是"再多撒点"，而是**重新分配容量**。

| 场景 | 对照 ctrl（q / B / 总分） | realloc 5%（q / B / 总分） | **realloc 10%（q / B / 总分）** |
|---|---|---|---|
| dl3dv/0f622ea | 15.67 / 36.1s / 29.39 | 16.63 / 35.7s / 30.43 | **17.22 / 31.4s / 32.03（+2.64）** |
| dl3dv/3e4dbe | 19.10 / 33.5s / 33.42 | 20.29 / 35.5s / 34.16 | **20.89 / 32.5s / 35.46（+2.04）** |
| hw/billboard | 35.89 / 26.7s / 52.16 | 36.37 / 27.4s / 52.47 | **36.66 / 24.7s / 53.36（+1.20）** |

**三例全胜，均值 +1.96 总分**，而且 **B 时间同时下降**（36.1→31.4、33.5→32.5、26.7→24.7）。
这与孔洞注入形成鲜明对比：注入是"加更多点"（质量 +0.3、时间翻倍、总分 −6），
重分配是"换更好的点"（质量 +1.4、时间还少 3 秒）。

**机理**：退役的低贡献基元（低不透明度×小尺度）在渲染中几乎不可见，却仍占用每步的光栅化与反向成本；
把名额给高残差区域的两个更小高斯，既补了细节又让 tile 覆盖更紧凑，所以质量与速度同时改善。

**待验证**：13 例全量复测、与其他配方项的交互、以及在 hw 类场景的最优比例（5% vs 10%）。

## 37. 重分配的 B 时间效应不可靠 —— 需要同会话配对重测

同一场景不同时段的测量显示 **B 时间波动极大**（同配方同场景 d0f：31.4s / 36.1s / 54.2s），
远超重分配本身可能造成的差异。这意味着 §35 里「重分配让 B 更快」的结论**不可靠**，
可能只是测量时段的 GPU 状态差异（时钟/共享）。

**稳定可信的结论只有质量项**：重分配在 6 个场景上质量分一致提升 +0.8~+2.8
（001dccbc 78.73→80.01、0b5635 29.68→32.17、bicycle 24.70→25.51、
0f622ea 29.19→32.03、3e4dbe 33.42→35.46、hw/billboard 52.16→53.36）。

**待办**：在同一会话内交替跑 ctrl / realloc15（同 GPU、相邻时段），用配对差值判定
TIME 项是否真的受损；只有质量增益能覆盖 TIME 损失时才并入交付配方。
在此之前，`run_pipeline.py` 的 realloc 默认值应视为**待验证**，不应作为定稿。

## 39. 【更正】fused Adam 从未真正启用 —— 之前的 24s 是噪声

代码核查发现两个问题，先后被 GPU 复现：

1. **第一次实现没有生效**：`torch.optim.Adam(旧 param_groups, fused=True)` 中，PyTorch 会保留
   每个 param_group 自己的 `fused` 值（默认 None），覆盖构造函数的 `fused=True`。
   所以日志里的 "rebuilt" 不能证明走了 fused kernel。
2. **修正后直接报错**：显式给每组设置 `fused=True` 后，内核真正被调用，但立刻失败：
   `RuntimeError: params, grads, exp_avgs, and exp_avg_sqs must have same dtype, device, and layout`。
   把参数统一转成 float32 后仍然失败，说明 FastGS 模型里存在参数/梯度 dtype 不一致
   （很可能部分张量是 float64）。

**结论**：
- 此前 "hw 上 fused 24.5s vs ctrl 32.3s" **不是 fused 的功劳**，只是 GPU 时钟状态差异；
- **fused Adam 在本模型上不可用**，已从交付配方中移除；
- 交付配方回到：5K 步 + LR 匹配 + 无 reset + λ_dssim 0.6 + scaling_lr 0.01 +
  结构操作前 1/4 + **realloc 15%** + 解码缓存 + SH 导出修正。

这条更正也提醒：以后凡是"只换 kernel 不改数学"的改动，必须先打印实际生效的配置
（如 `[g.get('fused') for g in opt.param_groups]`），再做计时归因。

## 40. 为什么 voxelfuse 无效：模块 B 的致密化把删掉的基元又造回来了

实测 train_record（bicycle）：

| 配置 | init 基元 | **最终基元** | 训练秒数 | 步数 |
|---|---:|---:|---:|---:|
| 原始 init + 5K | 520,980 | **1,000,104** | 34.3 | 5000 |
| fuse 0.85（442K）+ 5K | 442,747 | **894,926** | 28.2 | 5000 |
| fuse 0.85 + 7K | 442,747 | **1,113,134** | 42.7 | 7000 |

**结论**：FastGS 的结构阶段（前 1250 步）会把基元数量**翻倍**，realloc 再加 15%。
所以无论初始化是 52 万还是 44 万，跑完都收敛到 90~100 万——**初始压缩被模块 B 完全抹平**。

这同时解释了两件事：
1. **质量没有提升**：致密化由屏幕空间梯度驱动，会在同样的位置重新长出基元，融合掉的空间又被填回去；
2. **时间没有下降**：最终基元数几乎相同（895K vs 1.0M，只差 10%），单步成本自然差不多。

**正确的验证方式**：必须让压缩「保持住」——给模块 B 设基元上限
（`--max-gaussians <init_count>`），否则任何初始化侧的压缩都会在结构阶段被抵消。
这条也适用于之前所有"初始化侧减点"的实验（voxelmerge、prune 等）。

同场景、同 PLY、同 GPU，old（无 realloc）与 new（realloc 15%）**交替各两轮**：

## 42. gsplat 抗锯齿渲染：相机约定探测结果

为验证「LPIPS 差可能来自 FastGS 光栅化器缺少抗锯齿」这一假设，写了 `research/aa_probe.py`：
同一 PLY、同一批测试视角，用 4 种相机约定分别渲染并与 GT 比较 PSNR：

| 相机约定 | PSNR |
|---|---:|
| `w2c`（world_view_transform 转置） | **19.85（最优）** |
| `w2c_transposed` | 15.00 |
| `w2c_yflip` | 14.62 |
| `c2w`（求逆方向） | 15.03 |

**结论**：`w2c` 是正确约定（我们原来的用法没错），但仍有 **2.5 dB 的差距**（19.85 vs FastGS 的 ~22.4）。
剩余差异来自渲染器设置（FastGS 的 `mult` 缩放、near/far 语义、抗锯齿实现差异），
不是相机错误。**要把这条路线做干净还需要逐项对齐渲染器参数，成本明显高于剩余时间能承受的范围**，
因此本轮标记为「假设未验证」，脚本与探测方法留在 `research/render_gsplat_aa.py` / `research/aa_probe.py`
供后续接手。
